# Hostbeacon v1 spec

Status: **draft for sign-off**. Planning map: [Wayfinder: Linux host Agent + HACS Integration (v1 spec)](https://github.com/iwaneo/ha-linux/issues/1). Written in [Consolidate the v1 spec and get sign-off](https://github.com/iwaneo/ha-linux/issues/21).

This spec collects every v1 decision from the map in one place. Each section names the ticket that holds the full reasoning (table in §19). Where tickets changed each other, this spec states the **final** rule. Items marked *(new in this spec)* were decided while writing it (see §16).

This file holds no home network details, so it can be copied into the public product repo.

Terms (Host, Agent, Integration, Available update, Update run, Agent update, Host status, Action, Action log, Pairing, Pairing code, Host ID, Re-pair) are defined in [`CONTEXT.md`](../../CONTEXT.md). This spec uses them exactly.

## 1. What v1 is

Hostbeacon shows Linux servers in Home Assistant (HA): health, Available updates, Update runs, and a few controls. It has two parts:

- the **Agent**, a program installed on each Host;
- the **Integration**, an HA custom integration installed through HACS.

Project facts ([Public GitHub project…](https://github.com/iwaneo/ha-linux/issues/14), [Build new, or extend…](https://github.com/iwaneo/ha-linux/issues/10)):

- New code, not a fork. lnxlink, System Bridge, proxmoxve and TrueNAS are references only; copied code keeps its license notice.
- Name **Hostbeacon**, HA integration domain `hostbeacon` (cannot change after the first release).
- Public repo `hostbeacon` on GitHub, MIT license, copyright Tomer. Agent and Integration live in that repo.
- The planning repo (`ha-linux`) stays private because its issues hold home network details. Never copy its issues, history, or research branches into the public repo; copy only this spec and the ADR.
- Installed as a HACS custom repository first; submitted to the HACS default list after v1 is stable.
- No paid services. Code, CI, and releases are on GitHub (accepted lock-in).

### Out of scope for v1

- Windows and macOS; desktop features (media, screenshots, webcam, input, clipboard, brightness).
- Replacing the Proxmox VE or TrueNAS integrations.
- Hosts reached over the open internet without a VPN; setting up the VPN.
- Custom commands or scripts as HA buttons; Shutdown.
- Restart a service; Container start/stop/restart; container remove/prune.
- Linux without systemd (Alpine/OpenRC, Void), 32-bit ARM, the Agent inside a Docker container.
- Login history, "newer container image available", the full installed-package list.
- Choosing single packages to install; distro release upgrades; HA's "Create backup" option on update entities.
- Hostbeacon's own HA events, and notifications sent from HA to a Host *(new in this spec)*.

## 2. Supported Hosts

From [Which distros, CPU architectures, and environments…](https://github.com/iwaneo/ha-linux/issues/13) and [Where do the Hosts live…](https://github.com/iwaneo/ha-linux/issues/8).

| | Support |
|---|---|
| Debian/Ubuntu (apt), Fedora/RHEL family (dnf), incl. Proxmox VE, Raspberry Pi OS, AlmaLinux, Rocky | Full: sensors, Available updates, Update run, Actions |
| Other systemd distros (Arch, openSUSE, …) | Partial: Agent installs; sensors and Reboot work; Available updates and Update run show "not supported"; no promise |
| Read-only / image-based (Fedora Atomic/CoreOS, MicroOS) | Like partial. Not supported at all if `/usr/local` is not writable (unconfirmed) |
| Versions | Only releases that still get vendor security updates when v1 ships |
| systemd | Required. The installer stops with a clear message without it |
| CPU | x86-64 and ARM64 |
| Bare metal, VM | Full |
| LXC container | Supported. The Agent detects LXC and hides load, CPU temperature, and SMART. Reboot restarts only the container |

Networks: Hosts on HA's local network, or remote Hosts over a VPN the user runs (two-way reachable). Nothing is exposed to the internet; no broker; no Nabu Casa. Hosts can be added by address because discovery does not cross a VPN. Scale: up to about 100 Hosts per HA.

## 3. Architecture

From [Choose the Agent–HA architecture…](https://github.com/iwaneo/ha-linux/issues/15) and [ADR 0001](../adr/0001-integration-connects-to-agent.md).

- The Integration opens **one persistent WebSocket over TLS 1.3** to each Agent. The Agent pushes data on it; Actions and results use the same connection.
- One connection per paired HA per Host. On disconnect, the Integration reconnects with backoff. Its periodic tick only checks or re-opens the connection; it never polls data.
- The Agent listens on one TCP port (number picked in the build; the owner can change it).
- No plain-text mode, no fallback when verification fails.
- Rejected: MQTT in any form (needs a shared broker; MQTT discovery limits the update entity and would recreate all entities if adopted later), and the Agent connecting to HA (every Host would hold a powerful HA token).

## 4. The Agent

### 4.1 Language and parts

From [Which Agent language and install method…](https://github.com/iwaneo/ha-linux/issues/18) and [Lock the security and privacy model](https://github.com/iwaneo/ha-linux/issues/17) §1.

- Go, two static binaries (no cgo), amd64 and arm64.
- **Network part**: runs as system user `hostbeacon` (no login shell; not in `docker`, `disk`, or `adm`). Holds TLS, Pairing keys, and all message parsing.
- **Root helper**: built with no network code. Talks to the network part over a local socket that accepts only the `hostbeacon` user (`SO_PEERCRED`). It does only this fixed list of jobs:
  - read SMART; read container state; read the SMBIOS UUID;
  - Reboot; start the Update run unit; start the Agent update unit.
- The package list refresh (§4.6) is a separate fixed root timer, not a helper job, so nothing on the network side can start it *(new in this spec)*.
- The helper re-checks every request itself: Action enabled in the Host config, and every guard in §8 and §9. So a bug in the network part can only ask for what the owner enabled.
- No shell anywhere. Arguments are lists; names from data are checked against what the Host has.
- Every file that runs as root or that root reads (binaries, systemd units, Host config, Agent update staging area) is owned by root and writable only by root.
- The build picks the mechanism (helper daemon, or fixed systemd units behind a narrow rule) as long as these properties hold.

### 4.2 Host config

- Owned by root, not writable by the network part or HA. HA can read the enabled-Actions list (through `hello`) but never change it.
- **Enabled Actions**: Reboot, Update run, Agent update. Each is off until the owner turns it on.
- **Allowed source addresses**: by default only private ranges (IPv4 `10/8`, `172.16/12`, `192.168/16`; IPv6 `fc00::/7`, `fe80::/10`; loopback). `100.64.0.0/10` (Tailscale, also used by internet providers) is **not** allowed by default. The owner can add a single VPN address, narrow the list, or change it.
- **Package list refresh**: on by default on full-support distros; the owner can turn it off *(new in this spec, §4.6)*.
- If the Agent cannot read or understand the config, it refuses every Action and accepts no connections, and logs why (fail closed).

### 4.3 Install and owner commands

- Owners download the `.deb` or `.rpm` from GitHub Releases and run `sudo apt install ./hostbeacon_*.deb` or `sudo dnf install ./hostbeacon-*.rpm`. The package depends only on systemd and works offline. No install script, no apt/dnf repository.
- Docs show `sha256sum -c SHA256SUMS`, plus an optional `minisign` signature check.
- A `systemd-sysusers` step in post-install creates the `hostbeacon` user.
- Partial-support distros: tarball with the binaries, installed by `sudo ./hostbeacon install` (untested).
- The package asks nothing and enables no Action. `hostbeacon setup` then asks about each Action (default No), asks before opening a firewall port, and for Tailscale asks only for HA's single VPN address. It has a flags-only form for scripted installs.
- Owner commands (root): `setup`, `pair`, `pairings list`, `pairings remove`, `regenerate-key`, `status`, `update`, `install` (tarball), `reset-identity`, `keep-identity` (`--drop-missing`).
- Removing the package keeps the Agent instance ID; purging removes it (then it is like a reinstall).

### 4.4 Identity

From [Define the Agent–Integration contract…](https://github.com/iwaneo/ha-linux/issues/19).

- **Agent instance ID**: random UUID v4 made at first install, kept in the Agent's state directory. Never the hostname, IP, MAC, or `/etc/machine-id`.
- **Host ID**: set by HA to the instance ID at the first Pairing. It never changes after that (not with address, hostname, reinstall, or Re-pair). It is the HA config entry unique ID and device identifier. Entity unique IDs are `<Host ID>_<entity key>`.
- **Known IDs**: every instance ID the Agent has had and every Host ID it has been paired as. At each Pairing and Re-pair, HA tells the Agent the entry's Host ID.
- **Clone check**: at install, the Agent stores an app-specific hash of `/etc/machine-id` and, where present, of the SMBIOS UUID. At every start, **before accepting any connection**, it compares:
  - **Changed**: the Agent treats itself as a copy. It deletes its key, certificate, and all Pairings; makes a new instance ID, key, and certificate; moves all known IDs into its **copied-from list**; resets the Update run record to "no run yet"; and writes an Action log entry marking the copy.
  - **Cannot read a signal that was read at install**: **identity hold**. It keeps its credentials, accepts no connections (HA shows Offline), logs why, and `status` tells the owner what to run. It checks again at next start.
  - `reset-identity` does the "changed" path by hand. `keep-identity` stores the current fingerprint and ends identity hold (needs every signal readable). `keep-identity --drop-missing` removes an unreadable signal from the fingerprint, with a warning.
- **Undetected copies** (same machine-id and SMBIOS, e.g. a copied LXC): each Agent start makes a random **run ID**, sent in `hello`. If the Integration verifies two instances at once (two addresses both pass pin and key checks, with different run IDs), it stays on the saved address and raises the "two machines share the identity" repair (§7.7).
- **Accepted limit** (must be in the docs and in `reset-identity` help): clone detection is best effort. If the Agent does not detect the copy and HA does not reach both at once, HA cannot tell them apart. Docs tell owners to run `hostbeacon reset-identity` on every clone before it goes online.

### 4.5 What the Agent reads

From [Which sensors and controls are in v1?](https://github.com/iwaneo/ha-linux/issues/11), [How can an Agent read system telemetry…](https://github.com/iwaneo/ha-linux/issues/5), [How can an Agent read and run package updates…](https://github.com/iwaneo/ha-linux/issues/4).

- CPU usage, memory and swap, load (1/5/15), last boot time.
- Disk space per real mount (skip tmpfs, overlay, and other virtual mounts).
- Network traffic per physical interface (skip veth, Docker bridges, other virtual ones).
- CPU temperature, when the Host has a sensor.
- Failed systemd services (count and names).
- Reboot required: `yes` / `no` / `unknown`.
- Available updates (count, capped name list with versions, and a fingerprint of the full set).
- SMART per physical disk: OK/failing, temperature, SSD wear. Nothing on VMs/LXC without real disks.
- Containers (Docker/Podman): state of each (running, stopped, unhealthy).
- Environment (bare metal / VM / LXC), distro, architecture, kernel.
- The Agent detects its environment and every data source at runtime and reports each as a capability. A missing capability means "not supported here".

### 4.6 Refresh intervals, package list refresh, resource budget *(new in this spec)*

**Intervals** (fixed in v1; the build may tune them before release). The Agent samples each group on its interval and sends a `delta` only when a value changed after rounding: percentages and temperatures to whole numbers, rates to 3 significant digits. This keeps HA's recorder load low with 100 Hosts.

| Group | Interval |
|---|---|
| system (CPU, memory, load) | 30 s |
| network | 30 s |
| disks (space) | 60 s |
| temperatures | 60 s |
| failed services | on change (systemd signals), at most one delta per 10 s; full check every 60 s |
| containers | on change (Docker/Podman events), at most one delta per 10 s; full check every 60 s |
| SMART | every hour; never wakes a disk that is in standby |
| Available updates | re-read from the local package cache every 15 min, and after every Update run or list refresh |
| Reboot required | every 5 min, and after every Update run |
| newest Agent version | once a day (signed release check) |

**Package list refresh.** A plain Debian Host may never refresh its package list, so HA would show a false "0 updates". So on full-support distros, a fixed root systemd timer and unit refresh the list (`apt-get update` / `dnf makecache`) once a day, only if the list is older than 24 hours. It runs outside the Agent process and is never started by HA. It takes the same Hostbeacon package-task lock as the Update run and the Agent update (§8), skips its turn if that lock or the package manager's own lock is held, and is reported as `package_task_running` while it runs. The owner can turn it off in the Host config. The Available updates group carries the time of the last successful refresh; the Updates release notes show it. (The research found reading updates needs no root, but refreshing does; outbound traffic to the distro's repositories was already allowed in the security model.)

**Resource budget** (release gate):
- Agent, both parts together: at most 30 MB memory at idle and at most 1% of one CPU core on average with default intervals, measured on the arm64 CI runner and on the project's Debian and Fedora test Hosts. (Measured in research: about 13 MB.) A Raspberry Pi is not measured (no ARM test Host; §17).
- Integration: with 100 simulated Agents at default intervals, HA's added CPU stays under 5% of one core on average on the CI runner.

## 5. Pairing and credentials

From [Choose the Agent–HA architecture…](https://github.com/iwaneo/ha-linux/issues/15) and [Lock the security and privacy model](https://github.com/iwaneo/ha-linux/issues/17) §2.

- The Agent makes its own key pair and a long-lived self-signed certificate at install (never renewed). Private key file `0600`, owned by `hostbeacon`.
- **Pairing code**: shown by `hostbeacon pair` (or `setup`), run as root. 12 characters without look-alikes (no 0/O, 1/I/L), shown as 3 groups (e.g. `K7QM-4XPT-9RWD`). Lasts 10 minutes, works once, cancelled after 5 wrong tries. With no active code, the pairing endpoint refuses everything.
- The code authenticates both sides and binds the Agent's certificate fingerprint. It never crosses the network in the clear and is never a long-term key. The build picks the protocol (e.g. SPAKE2, or an HMAC over the fingerprint inside TLS) as long as this holds.
- Success creates one random 256-bit key per HA. It stays pending until HA confirms, over the pinned connection, that it saved the key and the pin; an unconfirmed key is dropped when the code expires.
- **On the Host**: only a hash of each key, plus the Pairing name, created date, and last seen time, readable only by `hostbeacon`.
- **In HA**: in the config entry (plain JSON, part of HA backups). Diagnostics redact it.
- **Pinning**: HA stores the certificate fingerprint. A different certificate later means HA refuses to connect and raises the certificate repair (§7.7). It never accepts a new certificate silently.
- Keys never expire and are never rotated automatically. A key stops working only when its Pairing is removed.
- **Several HAs**: one Host can pair with several HAs, each with its own code and key. Removing one does not affect the others. The enabled-Actions list is the same for all.
- **Revoke**: `hostbeacon pairings list` shows name, created, last seen; `pairings remove` deletes one and closes that HA's connection at once. Old Pairings are never removed automatically; `status` and the log warn about Pairings not seen for 90+ days.
- **Host removed in HA**: the Integration sends `pairing_remove`. If the Host is unreachable, the Pairing stays and HA shows a notification with the command to run on the Host.
- **Leaked HA key**: remove that Pairing on the Host, make a new code, Re-pair.
- **Leaked Agent private key**: `hostbeacon regenerate-key` makes a new key and certificate and removes every Pairing (it lists them first). Every HA must Re-pair. HA's certificate repair is only a reminder here.
- **Listening rules**: TLS only. Before a valid key, only the Pairing step is answered, and only while a code is active. Requests with a browser `Origin` header are rejected. Limits per Pairing on messages and Actions per minute (counted across reconnects) and on open connections; caps on connections that have not proved a key (total and per source address) with a short timeout. Numbers are set in the build (generous).
- **Replay**: everything is inside TLS; each Action has a unique ID and repeats are refused (§6.4).

## 6. Protocol

From [Define the Agent–Integration contract…](https://github.com/iwaneo/ha-linux/issues/19), with the changes from [How should a Host look in Home Assistant?](https://github.com/iwaneo/ha-linux/issues/20).

### 6.1 Format

- JSON text frames on the one WebSocket. Each message has `type`, `id`, and `kind`: `request`, `reply` (with the `id` it answers), or `event`. Size limit set in the build.
- Both sides ignore unknown fields. An unknown `type` is ignored; if it is a `request`, the receiver replies `unsupported`. The connection stays open.
- One JSON Schema plus example messages in the product repo. Agent tests and Integration tests use the same examples (contract tests).

### 6.2 Handshake

After TLS and the key check, the Agent sends `hello`: instance ID, run ID, copied-from list, hostname, Agent version, newest Agent version (`null` if unknown), supported protocol majors, environment, distro, architecture, capabilities, enabled Actions. The Integration answers with its version and supported protocol majors. Entities and buttons are built only from capabilities and enabled Actions.

### 6.3 State

- After `hello`: a full `snapshot`, then `delta` messages. A `delta` carries only changed groups, but **each group is complete** and replaces the old one. An item missing from a group no longer exists.
- Groups: agent (hostname, versions, capabilities, enabled Actions), system, disks, network, temperatures, failed services, containers, SMART, Available updates, Update run record, flags.
- Each value is a number, text, or `null` (unknown right now).
- Name lists (packages, services, containers) travel as a count plus a capped list.
- Available updates group: count, capped list (name, installed version, new version), fingerprint of the full set, last refresh time *(new in this spec)*.
- **Update run record** (kept on the Host, survives restarts): run ID; start and finish time; state `idle` / `waiting_for_lock` / `running` (+ percent) / `finished` / `result_unknown`; result OK or failed; installed and remaining counts; short error; "needs manual update" package names.
- Flags: package system broken (+ command to run), Reboot required `yes`/`no`/`unknown`, `package_task_running`, last boot time.
- Every reconnect's snapshot carries the current run record, so HA always re-reads it.

### 6.4 Actions

- `action_request`: `action_id` (UUID made by HA), Action (`reboot`, `update_run`, `agent_update`), HA user name or none. No target field in v1. "None" is logged as "no HA user".
- `action_ack`: `accepted`, or `refused` with a reason: `disabled`, `busy`, `update_run_running` *(new in this spec, to give the two different messages in §7.6)*, `too_soon_after_boot`, `cannot_log`, `duplicate`. Reserved, unused in v1: `not_allowed`, `unknown_target`.
- A `reboot` acceptance is the reboot acknowledgement. The result comes later as `action_result`, or for an Update run through the run record.
- **Repeated IDs**: the root helper checks the Action ID against the Action log and writes it there before running the Action, as one step under one lock. A repeat, even after a restart, is refused as `duplicate` with the first result if known. HA never retries an Action ID older than 1 hour.
- `pairing_remove`: the Agent deletes that Pairing's key and confirms.

### 6.5 Versions

- The protocol has its own `major.minor`, separate from release versions.
- A new minor only adds optional fields or message types. Different minors always work together; unknown features are hidden.
- A new major is breaking. The Integration supports at least the current and the previous major.
- **Limited mode** (no common major): the connection stays open with all security checks. Only `hello`, the `agent_update` Action messages, and `pairing_remove` are allowed; these never change in a breaking way. HA shows the Host Offline, raises the "update the Agent / update Hostbeacon" repair, and keeps the Agent update entity available.

## 7. The Integration in Home Assistant

From [How should a Host look in Home Assistant?](https://github.com/iwaneo/ha-linux/issues/20) ([prototype](https://github.com/iwaneo/ha-linux/blob/tomer/prototype-host-page/prototypes/host-device-page/index.html)) and [What do HA entity platforms and limits allow…](https://github.com/iwaneo/ha-linux/issues/7).

### 7.1 Adding a Host

- **Discovered**: the Agent announces itself with zeroconf/mDNS; HA lists it; the user clicks and enters the Pairing code. Discovery is never trusted by itself: it only offers to start Pairing.
- **By address**: IP or hostname, then the Pairing code. Always available (needed for VPN Hosts).
- **Address change**: for a paired Host, a zeroconf announcement may update the saved address only after the Integration connects there and the pin and key match. For Hosts added by address, the user edits the address in **Reconfigure**. If the Agent at the new address has a different certificate, Reconfigure hands off to Re-pair; it never replaces credentials itself.

### 7.2 Re-pair (HA re-authentication)

1. Address (pre-filled) and a new Pairing code.
2. HA shows the Agent's hostname: "Is this the same Host?" If the Agent reports a copied-from list: warning "This machine is a copy of another Host" and a required tick "It is the same machine". HA refuses if the new instance ID already belongs to another entry.
3. HA replaces address, pin, and instance ID. Host ID, entities, names, areas, automations, and history stay.

- Starts from the certificate repair or from Reconfigure.
- Re-pair never removes another Pairing by itself. If HA still holds the old key, it logs in with the new key, then with the old key, and sends `pairing_remove` for the old Pairing. Otherwise the owner removes it on the Host.

### 7.3 Device and entities

One HA device per Host. No child devices, no entity per service or container. `has_entity_name` on. Device name = hostname at Pairing, following later changes unless the user renamed it. Model = distro and version; software version = Agent version; hardware version = architecture; no manufacturer.

**Sensors** (enabled unless marked off):
- Host status: enum Online / Updating / Rebooting / Offline. Always available (§9).
- CPU usage; Memory usage (Memory used and Swap usage off).
- Load 1 min (5 and 15 min off); CPU temperature. Hidden where not reported (LXC).
- Last boot (timestamp). This is how v1 shows uptime.
- Disk `<mount>` used, per real mount (free space off).
- `<interface>` download / upload, per physical interface (byte totals off).
- Failed services (count; names as an unrecorded attribute).
- Containers running / stopped / unhealthy (counts; names and states as an unrecorded attribute). Only with the containers capability.
- Disk `<device>` health (problem), temperature, wear (SSD only). Only with real disks.
- Reboot required (Yes / No; unknown state when the Host cannot tell).
- Available updates (count).
- Last Update run: OK / Failed / Needs manual update / None yet (finish time, installed, left, short error as unrecorded attributes).

**Configuration** (entity category `config`, so Alexa/Google and "all buttons in this area" do not reach them):
- **Updates** (`update` entity). Install offered only when Update run is enabled on the Host; uses `PROGRESS`; release notes. Latest version text: "<n> updates · <short fingerprint>", so Skip hides only that exact set. Installed version text: "up to date". With zero Available updates, the latest version is also "up to date", so HA shows no update. The Integration overrides `version_is_newer()`: an update exists exactly when the two texts differ *(new in this spec: the zero case was not defined)*. Release notes (fetched when the dialog opens, never stored): package table (package, installed, new; capped with "+N more"), Reboot required, last run, package list age, a "Needs manual update" box with packages and command, and a line when Update run is off on the Host.
- **Agent** (`update` entity for Agent update). Install offered only when Agent update is enabled; otherwise the dialog says how to update on the Host. Stays available in limited mode.
- **Reboot** (`button`, restart class). Only when Reboot is enabled.

**Diagnostic**: Environment; Kernel, Protocol version, Last seen, Package list refreshed (all off).

Settings > Updates lists an update entity only when it has an update **and** is installable. So a Host appears there only when the matching Action (Update run, Agent update) is enabled. When the Action is off, the Updates and Agent entities still show on the device page and the Available updates count sensor stays. HA always shows Available updates and Reboot required, even when the matching Action is off *(corrects "one row per Host" in "How should a Host look", which did not account for HA's installable filter)*.

### 7.4 Names never in HA history

- HA history keeps counts, never lists of names (packages, services, containers). Names appear only where HA's recorder does not save them: unrecorded attributes and update release notes.
- No repair text or data ever holds a package, service, or container name (HA saves repairs to disk).
- This is why service and container Actions were removed: HA records every action call with its data.

### 7.5 Who may use an Action

- A call from a logged-in HA user (UI, app, typed Assist, API token): allowed only for admins. The Integration checks this itself for **all three** Actions, including Install on both update entities. HA core also makes install admin-only from 2026.9.0, but older HA versions do not, so the Integration never relies on it.
- A call with no user (automations, voice satellites, HomeKit, HA system calls): allowed (HA's own rule; HA cannot tell these apart). Nabu Casa Alexa/Google come from an admin system user and pass; HA VoIP voice uses a non-admin user and is refused.
- The Integration reads the caller from the entity context at the very start of the press, before any `await`.
- No extra confirm step. A dashboard card can add one.

### 7.6 Refusals

Shown as HA errors with a translated message:

| Reason | Message |
|---|---|
| not admin | "Only Home Assistant admins can reboot <Host>." (update entities: HA's own "Unauthorized" on 2026.9.0+, otherwise the Integration's own message with the same meaning) |
| `disabled` | "Reboot is turned off on <Host>. The Host owner can turn it on with `sudo hostbeacon setup`." *(changed during the build: names the command)* |
| `too_soon_after_boot` | "<Host> started less than 10 minutes ago. Reboot is possible after <time>." |
| `busy` | "<Host> is busy with a package task. Try again later." |
| `update_run_running` | "An Update run is already running on <Host>." |
| `cannot_log` | "<Host> refused: the Agent cannot write its Action log." |
| `duplicate` | the first request's result if known, else "This <Action> was already sent to <Host>. Waiting for its result." |

A button records "pressed" before the Integration can refuse, so the Integration also writes a logbook entry "<Action> refused: <reason>". On an Offline Host, entities are unavailable and HA skips presses silently.

### 7.7 Repairs and notifications

1. "Update run on <Host> is taking over 1 hour": warning; removed when the run ends.
2. "Package system on <Host> is broken": error, persistent, with the command to run; removed when fixed.
3. "<Host> needs a manual update": warning, generic text (the run would remove packages or change the distro release) and command; package names only in the Updates release notes. Removed when a later run passes its test step or no Available updates are left.
4. "Certificate of <Host> changed": error. Fix opens Re-pair (Integration repair flow). Warns not to Re-pair unless the Host was reinstalled.
5. "Two machines share the identity of <Host>": error; tells the owner to run `hostbeacon reset-identity` on the copy.
6. "Update the Agent on <Host>" / "Update Hostbeacon in HACS": error, limited mode.

Notification (not a repair): "Host removed, but its Pairing is still on the Host", with the command.

**No own events** *(new in this spec, Tomer's choice)*: v1 fires no Hostbeacon HA events. Automations use entity state changes (Host status, Last Update run, Failed services, Reboot required, Available updates).

### 7.8 Languages *(new in this spec, Tomer's choice; changed during the build)*

- All HA-facing text (config flow, entity names, states, errors, repairs, notifications) ships in **English only** (`strings.json`, `translations/en.json`). The first build also shipped Hebrew; Tomer dropped it.
- Agent command-line output and all docs are English only.

### 7.9 Diagnostics

"Download diagnostics" per Host redacts the Pairing key, Host address and hostname, IP and MAC addresses, disk serial numbers, and user names, also inside longer text. Neither side ever logs a key or Pairing code or puts one in a URL.

## 8. Update run

From [How do update runs and reboots behave?](https://github.com/iwaneo/ha-linux/issues/16).

- Only when Update run is enabled on the Host and the distro has full support.
- **One run per Host**: the root helper reserves the run slot first. A second Install, from any HA, is refused (`update_run_running`). Runs on different Hosts are independent.
- **Package-task lock**: the Update run unit takes the Hostbeacon package-task lock (shared with the Agent update and the list refresh timer) before step 1 and holds it until step 5 ends. The helper reports `accepted` only after the unit holds it.
- **Package manager busy**: wait up to 5 minutes for the package manager's lock (state `waiting_for_lock`). Still held: the run ends as failed with a "package manager busy" error, and installs nothing *(changed during the build, Tomer's choice: the run is already accepted by then, so it cannot be refused)*. Nothing is queued.
- **Steps**:
  1. Refresh the package list. On failure: stop, install nothing, report.
  2. Simulate the whole run.
  3. If apt would remove a package: stop, install nothing, show "Needs manual update" with the package names in the release notes. On dnf, obsoleted packages are replaced as normal; nothing else is removed. The same stop applies if the run could move the Host to another distro release *(new in this spec: guard for the locked "never a release upgrade" rule)*. Property: an Update run never changes the distro release. Check (the build may make it stricter, not weaker): on apt, after the refresh, every enabled package index whose Release file `Origin` is Debian or Ubuntu must have a `Codename` equal to the Host's `VERSION_CODENAME` from `/etc/os-release`, or that codename plus a suffix (`-updates`, `-security`, `-backports`). This catches a `stable` alias after a new Debian release and a source that points at the next Ubuntu release. On dnf, the Agent resolves `/etc/os-release` (following a symlink) and finds the package that owns that file with `rpm -qf`; the run stops if that package would change major version. If no owner is found, the run stops too (fail closed). The owner editing sources during a run is out of scope.
  4. Install all Available updates non-interactively: default answers, keep the Host's current config files. **Property:** what is installed is exactly the transaction the checks approved (same packages, full versions including epoch, release, and architecture, no removals), even if another tool refreshes the package list in between. The build picks how (for example: download the approved packages first and install only those files, or re-plan under the package manager's lock right before commit and stop if the plan differs), and adds a test on both test Hosts showing that a changed plan stops the run. The real install also refuses any removal (apt `--no-remove`).
  5. Re-read Available updates and Reboot required; store the result.
- Never a release upgrade. No per-package choice. Installs the newest versions at run time. Held-back updates (e.g. Ubuntu phased) stay listed.
- **Progress**: "Installing" with a percent where the tool gives one (apt), otherwise without. `update.install` waits until the run ends.
- **Survives restarts**: runs in its own root systemd unit. If HA's call ends first, HA shows "result unknown" until the Agent reports again. On reconnect, HA reads the run record.
- **Never stopped**, however long. After 1 hour: repair 1.
- **Result**: last run time, OK or failed, installed and left counts, short error. A failed Install also shows an HA error. A broken package system raises repair 2. No automatic retry, repair, or rollback.
- The Agent never changes the Host's own auto-updates (unattended-upgrades, dnf-automatic).

## 9. Reboot and Host status

From [How do update runs and reboots behave?](https://github.com/iwaneo/ha-linux/issues/16) and [Lock the security and privacy model](https://github.com/iwaneo/ha-linux/issues/17) §3.

- Only when Reboot is enabled. The Agent never reboots by itself (also not after an Update run).
- Refused while any package task runs (an Update run, an Agent update, the list refresh, or another tool holding the lock).
- Refused if the Host started less than 10 minutes ago.
- Orderly `systemctl reboot`, no delay.
- **Host status** (kept by the Integration, always available):
  - Online: connected.
  - Updating: an Update run is `waiting_for_lock` or `running`.
  - Rebooting: after an accepted Reboot, until the Agent reconnects with a new last boot time. The start time is saved, so this survives an HA restart. Not back within 15 minutes: Offline.
  - Offline: no connection, identity hold, or limited mode.
- While Offline, the other entities are unavailable.

## 10. Agent update and releases

From [Which Agent language and install method…](https://github.com/iwaneo/ha-linux/issues/18) and [Lock the security and privacy model](https://github.com/iwaneo/ha-linux/issues/17) §4.

- HA can only say "update the Agent". It never sends a URL, file, or code.
- The root helper starts a fixed root unit. The unit takes the package-task lock (the helper reports `accepted` only after that), downloads `SHA256SUMS` and its signature from a URL fixed in the binary into a root-owned staging directory, checks the minisign signature against keys compiled into the Agent, refuses downgrades, downloads the one file for this Host and checks its hash, installs it, restarts both parts, and rolls back to the previous version (kept in staging) if the health check fails.
- Install step: apt Hosts `apt-get install ./…deb`; dnf Hosts `dnf install ./…rpm`; tarball Hosts unpack into a new versioned directory and switch one symlink atomically (untested).
- **Rollback prerequisite** *(new in this spec)*: before installing, the unit makes sure the currently installed version is in staging. For `.deb`/`.rpm`, if it is not there yet (e.g. the first Agent update after a manual install), it downloads that version's package from its GitHub release and verifies it against that release's signed `SHA256SUMS`. If this fails, the Agent update stops before installing anything. Rollback: apt `--allow-downgrades`, `dnf downgrade`, or the tarball symlink (all untested). After success, the new version's package stays in staging for the next update.
- **State compatibility** *(new in this spec)*: all persistent data the Agent owns (Host config, identity, Pairings, run record, Action log) carries a format version. Within v1 a release may only add fields that the previous release ignores, so rollback to it keeps working. A change that breaks this needs its own ADR and a tested state restore before it ships.
- Owners update the Agent through HA or `sudo hostbeacon update`, never through `apt upgrade` (there is no repo).
- **Releases**: `.deb`, `.rpm`, tarballs on GitHub Releases; `SHA256SUMS` signed with minisign (Ed25519); GitHub attestations.
- **Keys**: release key (no password, so CI can sign) as the secret `MINISIGN_SECRET_KEY` in a protected `release` environment in GitHub Actions; no other copy exists. Backup key (password-protected) and its password in Tomer's 1Password, never as a plain file on a computer. Both public keys are compiled in; either can sign a release that replaces the key list.
- Build checklist: tag ruleset, tags only from `main`, owner approval for `release`, Actions pinned by SHA, 2FA/passkey.
- Accepted risks: the first install trusts HTTPS + GitHub. A taken-over GitHub account or leaked release key can push a signed bad update to every Host with Agent update enabled. If both keys are lost, owners reinstall by hand.
- The repo has `SECURITY.md` and GitHub private vulnerability reporting.

## 11. Action log

- The root helper writes every Action request to the system journal and to its own root-owned log file (rotated, kept 1 year): time, Action, which Pairing, the HA user name or "no HA user", accepted or refused (and why), result.
- HA cannot lower or turn off this log. The HA user name is HA's claim; the Agent cannot check it.
- If the entry cannot be written, the Action is refused (`cannot_log`).
- For an Update run, the result is written when it ends; if that failed, the helper logs it from the unit's status record at its next start or next successful write.

## 12. Security guarantees (summary)

- A hacked HA can do only what the owner enabled on each Host, within the guards. It cannot enable Actions, change the log, choose packages, or supply Agent code.
- A bug in the network part can only request what the owner enabled.
- Other local users cannot use the root helper.
- Reading the Host's key file does not let anyone connect as HA.
- Nothing is reachable from outside private ranges by default; config errors fail closed.
- Reboot at most about once per 10 minutes plus boot time.

## 13. Privacy

- Only paired HAs get Host data. No usage statistics, no crash reports. Other outbound connections: the distro's package repositories (refresh, Update run) and GitHub Releases (newest version check, Agent update).
- Only the data in §4.5 is sent. HA history keeps counts, not names (§7.4). Diagnostics are redacted (§7.9).

## 14. Testing and CI *(new in this spec)*

GitHub Actions (free for public repos) on every pull request:
- **Agent (Go)**: unit tests; a test for every root helper guard (fail closed, run slot, lock wait, simulation stop, reboot guards, duplicate Action IDs, log write failure, identity paths); static build for amd64 and arm64 (native arm64 runner).
- **Integration (Python)**: `pytest-homeassistant-custom-component` tests for config flow, discovery, Re-pair, Reconfigure, repairs, refusals, limited mode, and redaction; `hassfest` and the HACS validation action.
- **Contract tests**: both sides run the shared example messages from the JSON Schema.
- **Packages**: build `.deb`/`.rpm` and install them in containers of every supported release of Debian, Ubuntu, Fedora, and Rocky/Alma, on amd64 and arm64 (native arm64 runners).
- **Load test**: 100 simulated Agents against a test HA; checks the Integration budget in §4.6.
- **Agent budget check** (before each release): run the Agent for 1 hour with default intervals on the Debian and Fedora test Hosts and on a native arm64 CI runner; record memory and average CPU against §4.6. Native arm64 runners are free for public repos; a QEMU-emulated run does not count, and a release does not ship without this check.

Before each release (manual, real systemd): install, pair, sensors, Update run, Reboot, Agent update, Re-pair, and clone paths on the project's Debian and Fedora test Hosts with the project's test HA; HA screens checked.

## 17. Open risks and unchecked facts

- Name: official trademark databases (USPTO, EUIPO) not checked for "Hostbeacon".
- Untested on a live Host: dnf reading and Update run, the tarball install, read-only systems, x86-64 builds, Ubuntu, RHEL 10, the exact rollback commands, running under real systemd. Research measured in arm64 containers.
- Not confirmed: whether HA exposes `button`/`update` entities to Assist by default; whether every local HA backup is encrypted.
- Clone detection is best effort (§4.4).
- No ARM test Host: arm64 is tested only in CI containers, never on a real Raspberry Pi.
- No single reliable "reboot required" source on every distro, hence `unknown`.

## 18. Suggested build order

1. Product repo `hostbeacon`: license, `SECURITY.md`, CI skeleton, release signing setup.
2. Protocol: JSON Schema, example messages, contract test harness.
3. Agent network part: TLS, listening rules, Pairing, `hello`/snapshot/delta, sensors.
4. Root helper: jobs, guards, Action log, identity check.
5. Integration: config flow, Pairing, device and sensors.
6. Update run, Reboot, and refusals end to end.
7. Agent update and releases.
8. Re-pair, Reconfigure, repairs, limited mode, diagnostics.
